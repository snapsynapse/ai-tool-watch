# Reviewed publication
`node scripts/prepare-publication.js` is the only supported route from an accepted source/evidence update to a deployable `docs/` tree. It synchronizes canonical evidence, validates the changed source tree, generates the site/API, validates generated structure, and checks one implementation fixture through the human implementation page, API export, and MCP server input.
It writes `docs/publication-manifest.json`, whose SHA-256 inventory identifies the exact artifact, its starting source revision, and `reviewed_input_sha256`: the full canonical `data/` tree, generator `scripts/`, and README consumed by the build. Operational run receipts are excluded because the site generator does not consume them. GitHub Pages and the PAICE FTP target both download and verify the `reviewed-publication` artifact into a fresh directory produced by the same workflow run. Hidden files are included. Neither target rebuilds from source.
The workflow validates committed source/evidence before preparation, then stages `data/platforms/`, `data/watchlist/`, `data/evidence/index.json`, and `docs/` together when scheduled work produces a canonical update. A failed validator prevents artifact upload and therefore blocks both deployments.
The preparation job records the source commit, source tree, and artifact SHA-256 in the workflow summary after any bot commit, so hosted evidence can tie a deployed artifact to its exact committed tree.
This is a local and CI publication boundary. It does not claim a hosted deployment, notification receipt, stale-content remediation, or direct-email delivery. GitHub's native failure-email canary is already evidenced separately and is not repeated here.

## Existing signals and silence
`evidence-alerts.yml` reports records older than its declared 30-day threshold through a deduplicated GitHub issue. It is a stale-evidence review signal, not a direct email or proof that a record changed. `verify-features.yml` retains review and failure evidence, writes its workflow summary, and explicitly reports direct notification and missed-run monitoring as `not_configured`.

The native GitHub failure-email canary has already been received and confirmed by Sam. It establishes that GitHub's account notification route can report a deliberately failed workflow; it does not configure a repository-owned notifier, fallback, or missed-run observer. Healthy no-change and valid-idle runs stay silent by design. T12 does not send or schedule another canary, and it does not close the separately scoped direct-email and independent-monitoring work.
